Snowflake ETL PipelineCSV and PostgreSQL sources loaded into a Snowflake warehouse with star-schema modelling and SCD Type 2 history

§1Pipeline Architecture

Daily batch: CSVs land in an S3 staging bucket, PostgreSQL source is pulled incrementally via CDC timestamps. Python extracts using pandas and SQLAlchemy, normalises types, and emits to Snowflake via the native COPY INTO loader. MERGE INTO handles upserts with idempotency guarantees.

Figure 1. End-to-end data flow (batch cadence: nightly 02:00 ACST).

§2Star Schema

Fact table fact_sales centralises transaction events. Dimensions carry descriptive attributes and slowly-changing history.

Figure 2. Star schema. Solid lines denote foreign-key joins from fact to dimension.

§5Design Notes

  1. Staging tables use VARIANT type to tolerate upstream schema drift without blocking the load.
  2. CDC handled via updated_at watermarking — log-based CDC deferred until postgres WAL rates justify it.
  3. Idempotency guaranteed by MERGE INTO ... USING stg ON tgt.key = stg.key WHEN MATCHED ... WHEN NOT MATCHED .... Pipeline is safely re-runnable.
  4. Star schema chosen over snowflake schema — fewer joins, faster queries on Power BI and Metabase dashboards.
  5. SCD Type 2 applied to dim_customer, dim_product, dim_store. Date dimension pre-materialised for 10 years.
  6. All Snowflake compute uses an X-Small warehouse with auto-suspend at 60s — cost-controlled for development.
  7. Surrogate keys are sequences, not hashes. Hashes were considered but rejected for debuggability.
  8. Pipeline failures alert via GitHub Actions + a Slack webhook. Retries: 2 with 5-minute backoff.
